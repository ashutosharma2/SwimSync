# Build log (one line per session: date, what shipped, what I learned)

- 2026-10-21: Researched SwimSync and framed it around my own turned-away booking, without user research. Built the booking engine: a session-row lock, a counter, a cancel that only releases a confirmed booking, and idempotency keys, with 19 tests. Learned: a check-then-act race needs the check and the write in one locked step, and removing the lock from a throwaway copy proved the race tests really can fail.
- 2026-10-22: Added notifications through an outbox written in the booking transaction, a worker that retries with backoff, and an inbox that can't hold duplicates (28 tests). Built drill A (two instances behind HAProxy, one killed mid-load) and drew the architecture diagrams. Learned: holding a FOR UPDATE lock while waiting on another connection hung the tests; FOR NO KEY UPDATE fixed it, and pg_stat_activity showed why.
- 2026-10-23: Made drill A cut requests off mid-flight. Delaying every request overloaded the system at 100 ms and missed the moment at 20 ms; one targeted "victim" request, held before or after its commit, passed both ways. Learned: retries pile up when requests queue, and a run with no evidence of the risky case should say INCONCLUSIVE, not PASS.
- 2026-10-24: Hardened the API for database failures: statement and lock timeouts, an explicit commit, and two honest 503 answers ("database unavailable, not booked" and "outcome unknown"). Learned: libpq rounds a 1 s connect timeout up to 2 s, which I only found by measuring it.
- 2026-10-25: Built drill B with Toxiproxy (database down, database slow, and a commit whose reply gets swallowed). Every hard limit passed, but the outbox worker crashed when the database went down and never came back. Learned: statement_timeout only limits the database's own work, so it did nothing when the network was slow.
- 2026-10-26: Fixed the worker so it survives database outages with its own backoff; the drill B rerun delivered all 473 notifications. Learned: one failure path outside a try block can take down a whole process, and it took a drill to find it.
- 2026-10-27: Wrote the AWS design in Terraform and validated it locally without applying it: a VPC across two zones with public, app and database subnets, Session Manager through VPC endpoints instead of a NAT gateway, security groups that only allow the tier in front, an ALB, two instances with IMDSv2, and RDS with a password RDS manages itself. Added the AWS diagrams to the architecture doc. Built the first frontend: session cards with a water-level meter, a booking flow with 15 tests that never says booked or not booked without evidence, and swim passes with a QR code. In the browser, a stale screen offering the last place got "That last place just went" instead of an oversell. Put the frontend on hold while Figma Make designs the UI. Learned: the ₹0 budget comes from never applying, and "not booked" needs every attempt to have rolled back, because one uncertain attempt might have saved the booking.
- 2026-10-28: Set up CI with GitHub Actions. Every push to main runs three jobs: the 34 backend tests against a PostgreSQL 18 service container, the 15 frontend tests and a production build, and terraform validate with no AWS credentials. The workflow can only read the repo, and each job stops after 10 minutes so a hung test can't burn the free minutes. The first run passed in under a minute. Chose operator capacity changes as the next feature. Learned: the race tests need a real database because a mock can't hold a lock, and a job with no AWS credentials can check the Terraform without any way of reaching AWS.
- 2026-10-29: Added operator capacity changes. A cut cancels the newest bookings that no longer fit, each with a reason and an in-app notice, and writes an audit row, all in one transaction under the same session lock as booking. Closing a session cancels every booking the same way and refuses new ones. My bookings shows why a booking was cancelled, and the frontend treats a closed session as a final answer (45 backend and 16 frontend tests, passing in CI). Updated the README and the architecture doc, where drill B and the frontend were still drawn as planned. Learned: my first race test caught a missing lock in only 1 run out of 3, so I made it stricter until it failed 5 out of 5 without the lock. Capacity and the counter also have to change in one UPDATE, because PostgreSQL checks booked <= capacity after every statement.
- 2026-10-29 (evening): Built a one-file demo that runs the booking rules in the browser with made-up data, then brought its pool design into the React swimmer screen. Wrote up every decision so far as ADRs 001 to 015, each with its evidence and the date it was written. Added the operator change-log endpoint. Ran the whole app with Docker Compose, and on a one-node kind cluster that CI builds and books through on every push. Learned: Kubernetes found two gaps the drills hadn't. A rolling restart refused connections until each pod got a 5 s pause before stopping (4 errors in 308 requests without it, none in 291 with it), and a booking sent a quarter of a second after the pods reported ready still got a 502. Writing ADR-009 also showed the VPC endpoints aren't cheaper per hour than one NAT gateway, so the case for them is security.
- 2026-10-30: Added the operator endpoint that lists who holds a place in a session, oldest first, behind the operator token (52 backend tests), and started the operator screen. Built drill C for Kubernetes: a rolling update or a forced pod kill while 30 swimmers book through nginx, checked against drill A's hard limits. The dry run passed, and the real runs wait for my prediction. Learned: my kind cluster was gone after Docker Desktop restarted, so the deploy script has to be able to rebuild it from nothing.
